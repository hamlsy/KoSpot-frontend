# KOSPOT 점수 시스템 리팩토링 상세 기획안

## 1) 문서 목적

로드뷰 기반 위치 추적 게임의 점수 체계를 `정확도 중심 + 속도 보너스` 구조로 재정의하고, 현재 프론트엔드 구현(`src/features/game/single/roadview/utils/scoreCalculator.js`)을 기준으로 리팩토링 범위, 수식, 데이터 계약, 검증 전략, 릴리즈 절차를 명확히 정의한다.

---

## 2) 핵심 목표 (Objective)

1. **정확도 우선**
   - 위치 오차 거리의 최소화를 가장 중요한 실력 지표로 유지한다.
   - 속도 요소는 정확도를 침해하지 않는 보조 지표로 제한한다.

2. **긴장감 부여**
   - 동점 또는 유사 정확도 구간에서 변별력을 확보하기 위해 시간 보너스를 도입한다.

3. **긍정적 UX 제공**
   - 감점 방식 대신 보너스 배율 방식을 사용한다.
   - 늦게 제출해도 기본 점수(정확도 점수)는 보존되어 체감 박탈감을 줄인다.

---

## 3) 최종 점수 구조 (Core Mechanics)

최종 점수는 아래와 같이 계산한다.

```text
Final Score = Base Score (Distance) x Time Multiplier (Speed)
```

- 최대 점수: **1300점**
  - 조건: 거리 오차 0km + 유예 시간 내 제출
- 최소 점수: **0점**
  - 조건: 거리 오차 400km 이상

### 점수 해석 원칙

- 기본 점수는 실력의 본체(정확도)다.
- 시간 가중치는 성과 가속 장치(보너스)다.
- 가중치 하한을 1.0으로 두어 기본 점수 손실을 금지한다.

---

## 4) 거리 기반 기본 점수 정책 (Base Score)

### 4.1 거리-점수 앵커 테이블

| 거리 (km) | 점수 |
|---:|---:|
| 0 | 1000 |
| 1 | 950 |
| 5 | 900 |
| 10 | 800 |
| 30 | 700 |
| 50 | 600 |
| 100 | 400 |
| 200 | 200 |
| 400 이상 | 0 |

### 4.2 계산 방식

- 인접 앵커 구간에서 **선형 보간(Linear Interpolation)**을 적용한다.
- 1m 수준의 미세한 거리 차이도 점수에 연속적으로 반영한다.
- 구간 경계값(1, 5, 10, 30, 50, 100, 200, 400km)은 불연속이 없어야 한다.

### 4.3 예시

- 3km는 1km(950점)~5km(900점) 구간 보간
- 75km는 50km(600점)~100km(400점) 구간 보간

---

## 5) 시간 가중치 정책 (Time Multiplier)

시간 가중치는 **1.0 ~ 1.3** 범위를 갖는다.

### 5.1 유예 시간 (Grace Period)

- 기본값: **5초**
- 의도: 로드뷰 로딩/초기 탐색 시간 보장
- 규칙: 경과 시간 `elapsed <= grace`인 경우 배율은 항상 `1.3`

### 5.2 선형 감소 (Linear Decay)

유예 시간 이후 제한 시간까지 선형 감소:

```text
Multiplier = 1.0 + 0.3 x (timeLimit - elapsed) / (timeLimit - grace)
```

### 5.3 경계 조건

- `elapsed <= grace` -> `1.3`
- `elapsed >= timeLimit` -> `1.0`
- 계산 결과는 `min(1.3, max(1.0, value))`로 클램프

### 5.4 UX 원칙

- 빠르게 맞힌 사용자는 최대 30% 보너스를 받는다.
- 늦게 맞힌 사용자도 기본 점수 100%를 보장받는다.

---

## 6) 모드별 동적 호환 전략

시간의 절대값이 아니라 **남은 시간 비율**을 사용하므로, 모드가 달라도 동일 로직으로 동작한다.

1. **싱글 랭크 (180초)**
   - 5초 유예 후 175초 동안 완만하게 1.3 -> 1.0 감소
   - 정확도 중심의 신중한 플레이 유도

2. **멀티 쾌속 (60초)**
   - 5초 유예 후 55초 동안 빠르게 1.3 -> 1.0 감소
   - 순발력/판단 중심의 플레이 유도

3. **멀티 점수 환산**
   - `ConvertedScore = FinalScore x 0.08`
   - 멀티 전용 밸런스 계수는 서버 설정값으로 관리(하드코딩 지양)

---

## 7) 리팩토링 범위 및 설계 제안 (프론트엔드)

현재 `scoreCalculator.js`는 거리 점수(`calculateScore`)와 하버사인 거리 계산만 제공한다. 본 이슈에서는 아래처럼 역할을 분리한다.

### 7.1 모듈 구조 제안

- `calculateHaversineDistance(lat1, lng1, lat2, lng2)`
- `calculateBaseScore(distanceKm)` (기존 `calculateScore` 명확화)
- `calculateTimeMultiplier(elapsedSec, timeLimitSec, graceSec = 5)`
- `calculateFinalScore({ distanceKm, elapsedSec, timeLimitSec, graceSec })`
- `calculateModeAdjustedScore(finalScore, mode)` (멀티 환산 계수 반영)

### 7.2 데이터 중심 리팩토링

현재의 다중 `if-else` 구간 분기를 아래 형태로 데이터화한다.

```js
const DISTANCE_SCORE_POINTS = [
  [0, 1000], [1, 950], [5, 900], [10, 800],
  [30, 700], [50, 600], [100, 400], [200, 200], [400, 0],
];
```

- 장점
  - 점수표 변경 시 코드 수정 범위 최소화
  - OCP(개방-폐쇄 원칙) 친화적
  - 프론트/백엔드 앵커 테이블 정합성 점검 용이

### 7.3 반올림 정책

- 기본 점수: 소수 둘째 자리 반올림 유지
- 최종 점수: 제품 정책에 따라 아래 둘 중 하나를 명시
  - A안: 소수 둘째 자리 유지(클라이언트 표시)
  - B안: 정수 반올림(랭킹 저장값 일치)
- 권장: **서버 저장은 정수**, 클라이언트 표시는 소수 2자리 허용

### 7.4 책임 경계

- 프론트엔드: UI 즉시 피드백용 점수 추정
- 백엔드: 랭킹/보상 산정의 단일 진실 공급원(Authoritative)
- 서버 결과 수신 시 프론트 점수와 차이가 있으면 서버값 우선

---

## 8) 백엔드 구현 전략 정렬 포인트

문서 제안과 서버 전략을 다음처럼 맞춘다.

1. **거리 구간 탐색**
   - `TreeMap.floorEntry / ceilingEntry` 기반 O(log N) 탐색
   - 하드코딩 분기 최소화로 유지보수성 향상

2. **반올림 및 자료형**
   - 최종 반환은 `BigDecimal` + `RoundingMode.HALF_UP`
   - 랭킹 저장은 정수형(int)으로 정규화

3. **정합성 회귀 테스트**
   - 프론트와 동일 입력셋에 대해 허용 오차(또는 완전 일치) 검증

---

## 9) 수학/로직 검증 시나리오

### 9.1 거리 점수 검증

- 경계값: 0, 1, 5, 10, 30, 50, 100, 200, 400
- 근접값: 0.999, 1.001, 4.999, 5.001...
- 극단값: 음수 거리(0 처리), 10000km(0 처리)

### 9.2 시간 배율 검증

- `elapsed = 0`, `grace`, `grace + epsilon`, `timeLimit`, `timeLimit + epsilon`
- `timeLimit <= grace` 비정상 입력 안전 처리
  - 권장: 즉시 `1.0` 반환 또는 설정 검증 실패 처리

### 9.3 최종 점수 검증

- 정확도 동일, 시간만 다른 두 사용자 비교
- 시간 동일, 정확도만 다른 두 사용자 비교
- 400km 이상에서 시간 보너스 무효 확인

---

## 10) 밸런싱/게임디자인 관점 체크리스트

1. 상위권에서 시간 보너스가 과도한 역전 요소인지
2. 중위권에서 정확도 개선 동기를 해치지 않는지
3. 초보자 구간(100~300km)에서 점수 분포가 지나치게 평평하지 않은지
4. 모드별(싱글/멀티) 평균 라운드 점수와 분산이 목표 범위인지
5. 치팅/지연 제출(네트워크 지터) 보정 정책이 필요한지

---

## 11) 분석 이벤트(텔레메트리) 설계

운영 후 튜닝을 위해 최소 아래 필드를 수집한다.

- `distance_km`
- `base_score`
- `elapsed_sec`
- `time_multiplier`
- `final_score`
- `mode`
- `grace_sec`
- `time_limit_sec`
- `is_perfect_distance` (0km 근접 판정)

활용 지표:

- 모드별 평균 정확도/점수
- 유예 시간 내 제출 비율
- 동점 발생률 변화
- 시간 보너스 기여도 분포

---

## 12) 단계별 개발 계획

### Phase 1: 도메인 함수 분리

- `calculateScore`를 `calculateBaseScore`로 명명 정리
- `calculateTimeMultiplier`, `calculateFinalScore` 추가
- 기존 호출부 영향도 분석 및 어댑터 함수 유지

### Phase 2: 점수표 데이터화

- 구간 상수 -> 배열/맵 기반 앵커 포인트로 전환
- 선형 보간 공통 함수 재사용

### Phase 3: 모드 정책 분리

- 모드별 `timeLimit`, `grace`, `conversionFactor`를 설정 객체로 분리
- UI/도메인 로직의 하드코딩 제거

### Phase 4: 검증 및 릴리즈

- 단위 테스트 + 경계값 테스트
- 실제 플레이 로그 샘플로 회귀 시뮬레이션
- A/B 또는 소규모 카나리 릴리즈 후 전면 적용

---

## 13) 수용 기준 (Acceptance Criteria)

1. 거리 점수는 앵커 구간에서 선형 보간으로 계산되고, 경계 불연속이 없다.
2. 시간 배율은 1.0~1.3 범위를 절대 벗어나지 않는다.
3. 유예 시간 내 제출은 항상 1.3 배율을 받는다.
4. 400km 이상 오차는 시간과 무관하게 최종 0점이다.
5. 싱글/멀티 모드 모두 동일 로직으로 계산되며 모드 설정만 다르다.
6. 백엔드 최종값과 프론트 표시값의 불일치 정책(서버 우선)이 문서화되어 있다.

---

## 14) 리스크 및 대응

1. **리스크: 프론트-백 수치 오차**
   - 대응: 고정 테스트 벡터 공유, CI 비교 테스트 도입

2. **리스크: 모드 밸런스 쏠림**
   - 대응: 모드별 계수/유예시간 설정값 분리 운영

3. **리스크: 네트워크 지연으로 인한 체감 불공정**
   - 대응: 서버 수신 시각 기준 통일 + 허용 오차 정책 검토

4. **리스크: 지나친 속도 메타 고착**
   - 대응: 시간 보너스 상한(1.3) 유지, 정확도 테이블 우선 튜닝

---

## 15) 결론

본 리팩토링은 "정확도 중심"이라는 게임 본질을 유지하면서도 "속도 보너스"를 통해 경쟁의 긴장감을 높이는 구조다. 또한 보너스형 배율 정책으로 사용자 성취감을 보호하고, 데이터 중심 설계로 장기 유지보수성과 모드 확장성을 확보한다. 구현 시에는 프론트 즉시 피드백과 백엔드 권위 계산의 책임 경계를 명확히 하여 랭킹 신뢰성을 보장한다.
